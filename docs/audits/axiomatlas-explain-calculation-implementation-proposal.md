## 1. Expected User Experience & Interaction Design

1. **Reactive + Explicit Calculation Flow:**
   - AxiomAtlas currently evaluates inputs reactively (`75 ms` debounce in `bind()`, `site/assets/app.js` line 38). We preserve instant live calculation while adding a prominent **`Calculate / Explain Calculation`** action bar at the bottom of `.answer-card` (`site/assets/app.js` line 23).
2. **Progressive Disclosure via `#explain-drawer`:**
   - Whenever a calculation succeeds on any of the **133 explanation-supported calculators**, a button **`✦ Explain Calculation`** appears in `.answer-card` (`aria-expanded="false"`, `aria-controls="explain-drawer"`).
   - Clicking **`✦ Explain Calculation`** opens a structured, scannable derivation panel directly below the results (and stays synchronized if the user edits any input while the drawer is open).
   - If the current inputs produce a validation error (e.g., triangle inequality violation $a+b \le c$), the panel instead explains **why the domain constraint failed** and what condition must hold!

### 1.1 Ten Standardized Sections of Every Explanation Output

Where applicable to the calculator's domain, every generated explanation renders:
1. **Given Inputs:** User-entered values, symbols, labels, and selected units.
2. **Unit Conversions to Canonical SI (when non-default units are selected):** Exact conversion factor applied before formula evaluation (e.g., $v = 72	ext{ km/h} 	imes rac{1	ext{ m/s}}{3.6	ext{ km/h}} = 20	ext{ m/s}$).
3. **Formula Used:** Symbolic governing equation and theorem/law name.
4. **Values Substituted into Formula:** The governing equation with every variable symbol replaced by its numeric value.
5. **Step-by-Step Calculation & 6. Intermediate Values:** Ordered arithmetic/algebraic sub-expressions evaluated from the actual execution trace (`Step 1`, `Step 2`, ...).
7. **Mathematical / Physical Reasoning:** Brief domain justification (e.g., discriminant sign $\Delta > 0 \implies 2$ real roots; Reynolds/small-angle/annuity-due regime).
8. **Final Answer & Units:** Exact/full-precision IEEE-754 result alongside the display-formatted result (`fmt(v)`) and derived unit.
9. **Rounding & Precision Information:** States significant figures (`12 sig figs` / `max 9 fraction digits` in `fmt()`) or exact `BigInt` rational representation.
10. **Important Assumptions & Limitations:** Drawn from the calculator's `note` field and domain constraints (e.g., *"Ideal projectile in vacuum; neglects aerodynamic drag and Earth curvature"*).

## 2. Technical Architecture: Single-Pipeline Deterministic Trace Engine

### 2.1 Why a Single Evaluation Pipeline Is Mandatory

A common anti-pattern in calculator apps is computing the answer with one function and writing a separate string-template function to "re-compute" the explanation—which inevitably leads to rounding discrepancies or divergent bug behavior.

In our proposed architecture for `site/assets/engine.js`, **the explanation is a direct byproduct of the primary calculation**:
- `run(ast, vars, options, traceArray)` evaluates the compiled AST. When `traceArray` is omitted, `run()` executes with zero allocation overhead (fast path for 2,000-point graphing and 4,000-point root scanning). When `traceArray` is passed (for single-result evaluation in `.answer-card`), `run()` pushes each evaluated AST node (`{ op, symbolic, substituted, args, value }`) into `traceArray` as it walks the tree!
- Thus, the `finalValue` returned by `run()` is **guaranteed to be bit-for-bit identical** to the last step of `traceArray`.
